## Поток расчёта

1. Клиент получает каталог `/dem_sources` и выбирает доступную модель; предпочитается `GMTED2010_30sec`.
2. Координата переводится в CRS растра и привязывается к локальному максимуму накопления в пределах шага сетки.
3. WhiteboxTools выделяет водосбор в локальном окне. При необходимости окно расширяется; результат с неполным покрытием не выдаётся как успешный.
4. Общие тематические растры анализируются внутри границы. Геометрии слоёв готовятся отдельно от точной статистики.
5. Граница и слои передаются в `EPSG:4326`. Клиент показывает сводку, активный слой и экспортирует границу в GeoJSON.

Временные файлы расчёта отделены от рабочих растров. Смена точки или модели отменяет ожидание ответа на клиенте и защищает интерфейс от устаревшего результата; это не гарантирует немедленную остановку уже запущенного серверного вычисления.

## Запуск и конфигурация

Команды установки приведены в [README](../README.md#быстрый-старт). Проверенное окружение — Windows и Python 3.13. `requirements.txt` перечисляет зависимости без фиксации версий; полностью закреплённого Python-окружения пока нет. `frontend/package-lock.json` используется командой `npm ci`.

WhiteboxTools — отдельный исполняемый файл, вызываемый пакетом `whitebox`. При первом создании объекта пакет может скачать бинарник для текущей ОС. Если запуск завис на загрузке, проверьте доступ к сети и наличие исполняемого файла в окружении пакета. Подготовка накоплений через C# отдельно требует Windows/.NET Framework.

| Настройка | Где задаётся | Назначение |
|---|---|---|
| `WATERSHED_DEM_DIR` | Окружение backend | Внешняя папка `FlowDir`/`FlowAcc` |
| `VITE_API_URL` | Окружение Vite при запуске/сборке | Адрес API; по умолчанию `/api` |
| `DEM_FILES`, `DEFAULT_DEM_SOURCE` | `config.py` | Каталог и предпочтительная модель |
| `ELEVATION_RASTER`, `SLOPE_RASTER` | `config.py` | Общие растры рельефа |
| `SOIL_RASTER`, `LANDCOVER_RASTER` | `config.py` | Категориальные растры |
| `CLIMATE_TEMPERATURE_TEMPLATE`, `CLIMATE_RAINFALL_TEMPLATE` | `config.py` | Абсолютные шаблоны месячных серий с `{month}` |

Для отдельного адреса API запустите из папки `frontend`:

```powershell
$env:VITE_API_URL = 'http://127.0.0.1:5000'
npm run dev
```

Переменные Vite подставляются при сборке: изменение адреса после `npm run build` требует новой сборки. Прокси `/api` из `vite.config.js` относится к серверу разработки; готовая папка `frontend/dist` сама по себе не запускает backend и этот прокси.

`start-backend.ps1` запускает Python из `venv` в корне проекта и убирает `PROJ_LIB`/`PROJ_DATA` только из окружения запускаемого процесса, восстанавливая значения после завершения. Это предотвращает конфликт с системным `proj.db`, например из PostGIS. Системные настройки не меняются. Flask запускается как локальный сервер разработки.

## Основной API

Ниже указаны прямые пути Flask. При обращении через Vite используется префикс `/api`.

| Метод и путь | Параметры | Результат |
|---|---|---|
| `GET /dem_sources` | — | Каталог и доступность моделей |
| `GET /dem_coverage` | `source` | Обзорная геометрия покрытия |
| `GET /get_watershed` | `latitude`, `longitude`, `source` | Граница и анализ бассейна |
| `GET /terrain_value` | `latitude`, `longitude`, `layer` | Исходное значение высоты или уклона |

### Каталог и покрытие

`/dem_sources` возвращает `sources` и `default_source` (или `null`, если доступных моделей нет). Элемент каталога содержит `id`, `label`, `resolution_label`, `coverage_note`, `regional`, `flow_dir_encoding`, `available`, `unavailable_reason`, `grid_resolution_m`. Пути файлов в ответ не включаются.

`/dem_coverage?source=MERIT_3sec` возвращает `source_id`, `geometry` (GeoJSON FeatureCollection), `bounds` (`[west, south, east, north]` или `null`), `approximate`, `sample_resolution_m` и `note`. Сетка обзора ограничена 1024 ячейками по стороне. Геометрия разрезается на 180-м меридиане; восточная граница в `bounds` может быть больше 180° для удобного перехода карты. Первый запрос создаёт кэш и может быть медленнее последующих.

```powershell
Invoke-RestMethod 'http://127.0.0.1:5000/dem_sources'
Invoke-RestMethod 'http://127.0.0.1:5000/dem_coverage?source=MERIT_3sec'
```

### Водосбор и анализ

Все три параметра `/get_watershed` обязательны. Широта — в диапазоне −85…85, долгота — −180…180, `source` — доступный идентификатор каталога.

```powershell
$watershedResult = Invoke-RestMethod 'http://127.0.0.1:5000/get_watershed?latitude=55.74658358585305&longitude=37.65629073793753&source=GMTED2010_30sec'
$watershedResult.analysis
```

Пример требует покрытия данной точки локальными данными. Ответ содержит:

- `watershed` — GeoJSON FeatureCollection границы;
- `source` — `id`, `label`, `grid_resolution_m`, `regional` использованной модели;
- `analysis` — `area_km2`, `terrain`, `climate`, `landcover`, `soil` и слои `soil_map`, `landcover_map`, `elevation_map`, `slope_map`.

Климатические массивы идут в порядке январь–декабрь. Почвенная статистика содержит `status`, `categories` (`code`, `name`, `percent`), `coverage_percent`, `valid_cells`, `total_cells`, `reason`. Доли относятся к валидным ячейкам; `coverage_percent` может быть `null`, если покрытие оценить невозможно.

Слои содержат `status` (`ok`, `no_data`, `unavailable`), `geometry`, `approximate`, `sample_resolution_m`, `reason`. У категориальных слоёв свойства Feature — `code` и `name`; для покрова сервер передаёт английское название, а интерфейс связывает код с русской подписью и цветом.

У высот и уклонов дополнительно есть `unit` (`m` или `degrees`), `source_label`, `range` и `bands` — до 24 интервалов `code/min/max`. Верхняя граница включена только в последнем интервале. Постоянное поле даёт один интервал с равными границами. При недоступном слое геометрия и интервалы пусты, `range` равен `null`.

Ошибка параметров, недоступная модель или невозможность выделить полный водосбор дают HTTP 400 и JSON-поле `error`. Непредвиденная ошибка — HTTP 500 с общим сообщением и подробностями в журнале Flask.

### Значение под указателем

`/terrain_value` принимает координаты в тех же диапазонах и `layer=elevation` или `layer=slope`. Ответ: `status`, `value` (число или `null`), `unit`, `source_label`, `reason`. Читается окно 1 × 1 исходного разрешения с масками и NoData, без интерполяции.

Отсутствие данных или файла возвращает HTTP 200 со статусом `no_data`/`unavailable`; некорректные параметры — HTTP 400. Endpoint не строит бассейн и не ограничивает точку его границей. Это делает интерфейс, разрешая подсказки только внутри активной заливки.

## Проверки

Backend-тесты из корня проекта:

```powershell
.\venv\Scripts\python.exe -m unittest discover -s tests -v
```

Проверки frontend:

```powershell
Push-Location frontend
node --test src/lib/*.test.js
npm run lint
npm run build
Pop-Location
```

При конфликте PROJ в отдельной тестовой консоли временно уберите переменные текущего процесса:

```powershell
$env:PROJ_LIB = $null
$env:PROJ_DATA = $null
.\venv\Scripts\python.exe -m unittest discover -s tests -v
```

Большинство тестов создаёт небольшие синтетические растры. Проверки C#-ядра требуют Windows/.NET; отдельные интеграционные сценарии зависят от установленного WhiteboxTools. Реальные локальные растры не заменяются тестами.

Для аудита папки гидрологических оригиналов:

```powershell
.\venv\Scripts\python.exe scripts\audit_dem_sources.py 'D:\Hydrology\Data'
```

Скрипт читает метаданные и небольшие окна, проверяет облачные атрибуты, сетки пар и согласованность D8; результат выводится в консоль. Он не изменяет растры и не скачивает облачные заглушки.

В `scripts` сохранены инструменты сравнения COG, анализа и слоёв. Часть использует фиксированные наборы и локальные эталоны первоначальной миграции, не поставляемые в репозитории. В частности, `verify_terrain_cog.py` и `verify_thematic_cog.py` требуют локального API-fixture даже для создания baseline, а benchmark-скрипты по умолчанию ищут локальный эталон водосборов. Эти команды не входят в быстрый старт с чистого клона: сначала прочтите код и `--help`, подготовьте собственные исходники и эталоны.

## Экспериментальные модули

В коде сохранены `services/flood.py`, `services/buildings.py` и endpoint `/get_flood_risk`. Это заготовки HAND-сценария и оценки затронутых зданий. Они не подключены к рабочему сценарию интерфейса и не являются проверенной системой прогноза или денежной оценки ущерба.

Watersheds сосредоточен на восстановленной задаче магистерской: выделении и анализе водосборов. Дальнейшее моделирование наводнений и оценка ущерба развиваются в отдельном приложении. Общей точкой обмена может служить экспортируемая граница GeoJSON.
